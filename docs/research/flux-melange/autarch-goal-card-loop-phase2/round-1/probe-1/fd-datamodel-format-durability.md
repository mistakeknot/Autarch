## Findings

### uncrancher-declined-fields-not-r3-forced
- **Severity:** P1 (as originally claimed) — **verdict: REFUTED**
- **Where:** `product-card-format.md` Shape section (unc-rancher YAML) + §Card status; `dotfiles/common/.local/bin/card-check.py:198-209` (R3)
- **What:** The prior claim asserts confirming uncrancher's card is "review four, then originate success from nothing, then originate a dependent guardrail, a sequential chain R3 forces into one sitting." Read against the actual code and prose, this is wrong on both halves:
  1. **R3 does not require success/guardrail to leave `declined`.** `card-check.py:198-205` builds `drafted = [n for n in FIELDS if states[n] == "drafted"]` and raises only if that list is non-empty. A field in state `declined` is never in that list — it satisfies R3 permanently, with zero further action. The format doc says this outright: *"A card may be confirmed with `success` and `guardrail` declined. That is mk saying, on the record, 'I do not yet know how I would tell if this worked.'"* Confirming uncrancher's card, as drawn from the measurement (line/persona/pain/cuj drafted, success/guardrail never drafted at all — the drafter declined them per R1/R2), requires ratifying exactly the four drafted fields. Success and guardrail can be left declined forever; nothing "originates."
  2. **The "dependency" is prose, not a rule, and R3 has no session semantics to force anything "into one sitting."** `guardrail.needs: "Resolution of success first"` is free text inside one field's `declined` block. `validate()` never reads or enforces `needs` for any cross-field ordering — grep the full `FIELDS` loop (`card-check.py:139-183`) and R3 (`:197-209`): neither references `needs` at all. It is the drafter's own rationale for *this* instance, not a format invariant; a different card could carry `guardrail: confirmed` next to `success: declined` and pass cleanly. Separately, each field carries its own independent state (`drafted | declined | confirmed`) and `validate()` re-reads whatever is on disk at invocation time with no memory of prior runs — a human can confirm persona today, pain next week, and flip the card-level `status: confirmed` whenever the last drafted field clears. There is no mechanism in this file that forces a single sitting.
- **Evidence:** `card-check.py:198-209` (R3 body, quoted above); `product-card-format.md` §Card status ("A card may be confirmed with success and guardrail declined..."); the same YAML block's `guardrail.needs` value; absence of any `needs`-reading code in `validate()` (`card-check.py:110-214`, confirmed by full read).
- **Suggestion:** n/a — this is a correction, not a defect to fix in the target artifacts.
- **Remediation:** Drop the "sequential-origination-forced-into-one-sitting" framing from any ruling this goal produces about confirm-step cost — R3 mechanically permits leaving success/guardrail declined, so the cost driver (if real) is ratifying four already-drafted fields, not originating two new ones.

### worked-example-understates-real-ratification-surface
- **Severity:** P2
- **Where:** `product-card-format.md` §Shape (the sole YAML fenced block, `project: unc-rancher`) vs. the proposal's own measurement table (`docs/proposals/2026-08-13-goal-card-loop-phase2.md`, uncrancher row)
- **What:** The format doc's only worked example — the canonical thing a reader forms their mental model of "confirming a card" from — reuses `unc-rancher` by name and by pain/persona content, but shows a state distribution that does not match what the real drafter run actually produced for that project. The doc's example: `persona: drafted`, `pain: confirmed`, `cuj: confirmed`, `success: declined`, `guardrail: declined` — only **one** field (`persona`) still needs to leave `drafted` before R3 passes. The measurement table's real uncrancher row: `line: D, persona: D, pain: D, cuj: D, success: —, guardrail: —` — **four** fields (`line`, `persona`, `pain`, `cuj`) sit in `drafted`, none pre-confirmed. A reader (mk, or an agent estimating scope before the goal runs) who forms expectations from the doc's own illustration would anchor on "one field to review," not four — a 4x understatement of the actual ratification surface this goal's real first card presents.
- **Evidence:** `product-card-format.md` Shape YAML (`pain: {state: confirmed, ...}`, `cuj: {state: confirmed, ...}`) vs. proposal's measurement table row `uncrancher | D | D | D | D | — | —` (line/persona/pain/cuj all D, i.e. drafted).
- **Suggestion:** Either regenerate the Shape section's worked example from the actual drafter output for uncrancher (all four non-declined fields shown as `drafted`, matching the measurement), or add one sentence noting the example is a hypothetical mid-review snapshot, not the drafter's raw output — before the goal's confirm-step cost measurement is recorded against it.

## Verdict
The prior P1 claim is refuted at the mechanism level: R3 only blocks on fields still `drafted`, treats `declined` as a permanent, explicitly-sanctioned terminal state, and has no session/temporal semantics to force anything into "one sitting" — so confirming uncrancher's card is "ratify four drafted fields," not "ratify four, then originate two more." The residual, genuinely live risk in this territory is documentation fidelity, not validator mechanics: the format doc's sole worked example understates the real drafted-field count by 3 and the doc never shows a terminal confirmed instance at all — both cheap to fix before the goal's cost measurement and the phase-2 TUI take the doc as ground truth.
