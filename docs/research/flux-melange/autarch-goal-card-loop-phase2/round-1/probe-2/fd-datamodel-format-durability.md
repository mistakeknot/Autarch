## Findings

### coverage-fraction-asymmetry-confirmed
- **Severity**: P1
- **Where**: `docs/proposals/2026-08-13-goal-card-loop-phase2.md` lines 41-44 (preceding paragraph) and line 54 (DONE WHEN)
- **What**: CONFIRMED. The proposal names the failure it is fixing in explicit terms — "Coverage is stated as a fraction with every unresolvable session named, never dropped — intermux reports 1 of 21 and discloses no gap, which is the failure this row is replacing" (lines 42-44) — and DONE WHEN operationalizes exactly one coverage-fraction requirement: "the TUI renders all 21 sessions as project rows with a stated coverage fraction" (line 54). That fraction is scoped to *session-to-row enumeration completeness* (did every live session become a row), not to *card-confirmation state* (how many of those rows have a confirmed/provisional/invalid/absent `docs/why.md`) — which is the actual axis ruling 11's ordering runs on (`strength.score` from `card-check.py --json`, lines 41-42) and the axis the whole goal is diagnostic about. The nearest DONE WHEN clause that touches card state, "a project whose card is absent, provisional, invalid and confirmed are four visibly distinct row states" (lines 55-56), requires only per-row visual distinctness, not an aggregate disclosure statement (e.g. "3 confirmed / 0 provisional / 2 invalid / 16 absent of 21"). A TUI can satisfy every DONE WHEN clause — four different row colors, a session coverage fraction printed once — while never surfacing what fraction of the 21 (let alone the 82-project estate this design is ultimately for) actually have a ratified why. That is structurally the same silent-gap failure the proposal indicts intermux for, just moved one field over: intermux drops sessions silently; this TUI, as specified, is permitted to drop *card coverage* silently while looking compliant on every checkable line.
- **Evidence**: `docs/proposals/2026-08-13-goal-card-loop-phase2.md:42-44` (coverage-fraction principle stated, scoped to sessions) vs. `:50-57` (full DONE WHEN list — no clause requires a stated count/fraction of confirmed-vs-absent-vs-provisional-vs-invalid cards among the rendered rows, only visual distinctness per row). Cross-checked against `dotfiles/common/.local/bin/card-check.py:43,217-238` — the four-verdict data (`CONFIRMED, PROVISIONAL, INVALID, ABSENT = 0, 1, 2, 3`) needed to compute such an aggregate already exists per-row via `--json`; DONE WHEN simply never requires it be summed and printed.
- **Suggestion**: n/a (confirmation of prior finding; remediation captured below).
- **Remediation**: Add a DONE WHEN clause requiring the TUI to state a card-coverage fraction (e.g. "N of 21 rows have a confirmed card; M absent; K provisional; J invalid") with the same never-drop discipline already required for session enumeration, so the row that replaces intermux's silent 1-of-21 does not reproduce the same silence one field over.

### format-finding-recorded-not-gated-before-tui-build
- **Severity**: P1
- **Where**: `docs/proposals/2026-08-13-goal-card-loop-phase2.md` lines 34-39 (the "answer the question one real card raises" paragraph) and line 53 (DONE WHEN); `dotfiles/common/.local/bin/card-check.py:118-121`
- **What**: The proposal's own prose states the sequencing rationale precisely — confirm one real card, surface a format finding if the six-field shape doesn't fit, "and it is cheaper now than after the TUI reads it" (lines 36-37) — then "Then build phase 2" (line 39) immediately after, in the same goal. But DONE WHEN only requires that "the confirm-step cost and any format findings are written into the brainstorm as rulings with reasons" (line 53) — recorded, not resolved or implemented — before the TUI-build clauses (lines 54-57) are satisfied. `card_version` is a hard equality pin with no migration path (`card_version is {card.get('card_version')!r}, expected 1` — card-check.py:118-121; no version-2 handling anywhere in the validator). If unc-rancher's confirm step is the first one to surface a real format finding (plausible: `success` drafted 0/5 across all five measured repos, so the field the goal calls "the one the whole premise depends on" is the most likely to need a shape change), that finding becomes a ruling-with-reasons on schedule — but nothing in DONE WHEN blocks the phase-2 TUI build from proceeding against the pre-finding v1 shape within the same goal. That is the exact pattern this lens exists to catch: a v1 schema hardening around an early (here, n=1) confirmed sample before the second consumer (`pkg/tui`) locks in, with no coded path to reconcile the two if they diverge inside one goal's lifetime.
- **Evidence**: `docs/proposals/2026-08-13-goal-card-loop-phase2.md:36-37` (format findings explicitly framed as cheaper-before-TUI) vs. `:39` (TUI build follows in the same goal) vs. `:53` (DONE WHEN requires findings only be *written as rulings*, not acted on); `card-check.py:118-121` (no `card_version` migration path exists to act on such a finding even if DONE WHEN required it).
- **Suggestion**: If a format finding surfaces during unc-rancher's confirm step, treat resolving or explicitly deferring it (with a stated reason it's safe to defer past a v1-hardened TUI) as a precondition on the TUI-build DONE WHEN clauses, not a parallel-track recording — otherwise "cheaper now than after the TUI reads it" is a stated goal the DONE WHEN list doesn't actually enforce.

### ranking-checkbox-trivially-satisfied-at-zero
- **Severity**: P2
- **Where**: `docs/proposals/2026-08-13-goal-card-loop-phase2.md` line 55 (DONE WHEN: "ranking matches ruling 11 against real card strengths"); line 47 (OUT: "backfilling cards beyond the one confirmed"); `dotfiles/common/.local/bin/card-check.py:217-238` (`strength()`)
- **What**: `strength()` counts only `confirmed` fields ("Only `confirmed` counts... neither is a project that knows what it is for," card-check.py:224-228). OUT explicitly excludes backfilling any card beyond the single unc-rancher confirm (line 47), and ruling 12 (cited lines 116-118) forbids bulk drafting besides. So of the 21 rendered project rows, at most one (unc-rancher) will have any confirmed fields; the other 20 will be absent or, at best, provisional-with-zero-confirmed, all scoring `strength.score = 0`. DONE WHEN's "ranking matches ruling 11 against real card strengths" is checkable in the narrow sense (assert the sort order), but with 20 rows tied at an identical zero, the comparative "weakest card first" logic ruling 11 actually specifies is never exercised between two differently-scored non-zero cards — the pilot proves the ranker can place one non-zero score correctly among zeros, which is a much weaker claim than "the ranker orders real card strengths," the language DONE WHEN uses.
- **Evidence**: `docs/proposals/2026-08-13-goal-card-loop-phase2.md:41-42` (ruling 11 ordering, "weakest card first") + `:47` (OUT excludes further confirms) + `:55` (DONE WHEN ranking clause); `card-check.py:230-238` (`strength()` — confirmed-only scoring, so absent/provisional cards all report `score: 0`).
- **Suggestion**: Either reword the DONE WHEN clause to state its actual scope ("ranking places the one confirmed card correctly relative to 20 zero-score rows") or accept as a known limitation that the multi-card comparative-ranking claim stays unverified until a second card is confirmed — don't let the pilot's green checkmark be read as evidence the ranker generalizes across differently-scored real cards.

## Verdict
The prior finding is CONFIRMED: the proposal states a never-drop coverage-fraction discipline in its own preceding paragraph and applies it only to session enumeration, leaving DONE WHEN with no equivalent aggregate disclosure for card-confirmation state — the axis the goal actually exists to measure. Two further findings extend the same lens: DONE WHEN lets phase-2 TUI-build clauses proceed without gating on resolution of any format finding the confirm step surfaces, against a card_version pin with no migration path (P1); and the ranking DONE WHEN clause is satisfiable in a way that proves far less about ruling 11's comparative logic than its wording implies, given OUT's one-confirm-only scope (P2).
