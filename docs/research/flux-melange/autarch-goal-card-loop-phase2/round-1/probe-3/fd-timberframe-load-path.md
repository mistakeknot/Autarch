## Findings

### flat-done-when-no-raising-order
- **Severity:** P0
- **Where:** `docs/proposals/2026-08-13-goal-card-loop-phase2.md` — goal text lines 24-38 (confirm step + format-finding question) transitions at line 39 ("Then build phase 2") into the DONE WHEN list at lines 50-63, which lists "the confirm-step cost and any format findings are written into the brainstorm as rulings with reasons" (line ~53) as one item among six flat clauses alongside "the TUI renders all 21 sessions..." and "ranking matches ruling 11..."
- **What:** The goal's own rationale states the format finding must land "cheaper now than after the TUI reads it" (line 32-33) — but DONE WHEN is a flat, unordered checklist, not a staged gate. Nothing in the acceptance criteria requires the format-finding ruling to be *written and ratified before* pkg/tui begins consuming the format. An executing agent satisfying every DONE WHEN clause in any order — including building the TUI first, or concurrently with the confirm step — completes the goal exactly as written. The prose says "then... then... then build phase 2"; the checklist that actually gates completion carries no such dependency.
- **Evidence:** Compare the goal's own stated purpose (line 32-33: "that is a format finding and it is cheaper now than after the TUI reads it") against the DONE WHEN list at lines 50-63, where the ruling-write clause and the TUI-render clause are two items in one unordered set, joined by semicolons with no sequencing language. This is exactly the scenario this lens's own severity calibration names as P0: "If phase 2 begins before the confirm-step format finding is written into the brainstorm as a ruling, or if the goal is executed as one continuous stretch with no stop between confirm and build." Nothing in the document's machine-checkable criteria prevents either.
- **Suggestion:** Split DONE WHEN into two ordered gates within the same goal — Gate A (card drafted, confirmed, format finding recorded as a ruling, confirm-step cost recorded) must close, with an explicit mk checkpoint, before Gate B (pkg/tui work) opens. Smallest viable fix: one sentence in the goal text making the ruling-write a hard precondition for touching `pkg/tui`, not a co-equal checklist item.

### undrafted-fields-may-invalidate-not-provisionalize
- **Severity:** P1
- **Where:** `dotfiles/common/.local/bin/card-check.py:131-137` (`fields = card.get("fields")` … `missing = [f for f in FIELDS if f not in fields]` … `raise CardError(f"fields missing entirely: ...")`); confirmed by `dotfiles/common/.claude/hooks/tests/test-card-check.sh:511-527` (`test_missing_field_is_refused`, asserts `rc == "2"`); the measurement table in the proposal (repo table, uncrancher row) shows `success` and `guardrail` as never drafted for `uncrancher`; `Sylveste/apps/Autarch/docs/reference/card-drafter.md` is not present in the local tree (only in commit `38715de`, not an ancestor of local `main`)
- **What:** `card-check.py` requires all five `FIELDS` keys (`persona`, `pain`, `cuj`, `success`, `guardrail`) to be present in the `fields` mapping — with *some* state, drafted or declined — or it raises `CardError` and the gate reports **INVALID** (exit 2), not **PROVISIONAL** (exit 1). The test suite the validator ships with encodes this as intentional behavior (`test_missing_field_is_refused` expects `rc == 2`). unc-rancher's card, per the proposal's own measurement, has never had `success` or `guardrail` drafted. For the freshly-drafted card to validate as PROVISIONAL rather than INVALID, the drafter must proactively write full `declined` blocks (`state`, `reason`, `needs`) for both fields the moment it runs — not merely leave them out because it "couldn't draft" them. Whether `card-drafter.md` actually does this is unverifiable from the local tree: the file lives only in a commit that is not an ancestor of local `main`. If it does not, the very first invocation of this apparatus against its flagship pilot subject returns INVALID — and `guard-plan-needs-card.sh` (line 79) surfaces a materially harsher message ("is INVALID: <verdict>") than the PROVISIONAL path (line 78, "drafted by an agent, not yet confirmed by mk"), on the goal's first real run.
- **Evidence:** `card-check.py:135-137` — the missing-field check fires before any per-field state logic runs, so it cannot distinguish "field omitted" from "field the drafter chose not to attempt." `test-card-check.sh:511-527` demonstrates this is a deliberately tested contract, not an oversight. The proposal's measurement table shows `success` at 0/5 drafted across all five repos and `guardrail` absent for `uncrancher` specifically — i.e., exactly the condition that triggers the missing-field path if the drafter leaves the keys out.
- **Suggestion:** Before running the confirm step against unc-rancher, read `card-drafter.md` (from `38715de` or wherever it actually lands) and verify it stubs every undrafted field as `declined` with `reason`/`needs`. If it does not, that is itself the day-one format finding to record — cheapest to catch by dry-running the drafter against unc-rancher and checking the exit code before scheduling mk's confirm session, not by discovering it live.

### out-list-forecloses-two-of-four-row-states
- **Severity:** P1
- **Where:** `docs/proposals/2026-08-13-goal-card-loop-phase2.md:46` (OUT: "backfilling cards beyond the one confirmed") vs `:55-56` (DONE WHEN: "a project whose card is absent, provisional, invalid and confirmed are four visibly distinct row states")
- **What:** DONE WHEN asks for four *visibly distinct* row states to be demonstrated, which — read alongside the goal's repeated insistence on live sessions over fixtures (line 51: "both from a live session rather than a fixture") — implies real cards in each of the four verdicts. But OUT explicitly bars drafting cards for anything beyond the one confirmed subject. Verified directly against the local checkouts: no `docs/why.md` exists today in any of `uncrancher`, `shadow-work`, `jeddnet`, `ravenous`, or `jawnomicon` (checked all five paths on disk) — the measurement table is analysis output, not artifacts on the filesystem. Under this goal's own scope, at completion the only reachable states among the 21 real sessions are CONFIRMED (unc-rancher, exactly one) and ABSENT (everything else, since no other repo gets a card drafted at all). PROVISIONAL only exists transiently, mid-confirm, on unc-rancher's own card before mk ratifies it — gone by the time DONE WHEN is checked. INVALID has no natural path to appear on any real project without someone deliberately corrupting a card, which is also outside scope. Three of the four states this clause demands have no real subject to render.
- **Evidence:** Direct filesystem check: `find` for `docs/why.md` under `/Users/sma/projects/{shadow-work,jeddnet,uncrancher,ravenous}` and `/Users/sma/projects/uncrancher/data/jawnomicon` — none exist. OUT list line 46 forbids producing more. DONE WHEN line 55-56 asks for all four states "visibly distinct" without qualifying "or demonstrated via a held-out fixture card," which is the escape hatch the rest of the goal explicitly rejects elsewhere (line 51).
- **Suggestion:** Either (a) amend OUT to permit drafting-without-confirming on 2-3 additional repos specifically to populate PROVISIONAL and INVALID states honestly (a narrower carve-out than "backfill," since nothing gets confirmed), or (b) reword the DONE WHEN clause to say explicitly that PROVISIONAL/INVALID are verified via a held-out test card rather than a live project, so the acceptance criterion doesn't silently fail or get satisfied by a code-reviewer's eyeball instead of real data.

## Verdict
The frame's biggest risk isn't the six fields — it's that the goal's own acceptance criteria don't enforce the raising order its prose narrates: nothing stops phase 2 from reading the format before mk's format-finding ruling is on record, which is precisely the P0 this lens exists to catch. Two more joints read tight but may not carry the load intended: the confirm step's first real run risks an INVALID verdict card-check.py's own tests predict, on a drafter procedure this review can't inspect, and the "four visibly distinct row states" clause asks the goal to demonstrate stock (provisional, invalid cards) that its own OUT list refuses to produce.
