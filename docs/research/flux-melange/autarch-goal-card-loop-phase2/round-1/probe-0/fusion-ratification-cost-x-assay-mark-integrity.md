## Findings

### r3-decline-escape-reconciled
- **Severity:** P1
- **Where:** `dotfiles/common/.local/bin/card-check.py:172-179` (declined branch), `:197-209` (R3 ratified), `:185-195` (R4 line)
- **What:** f-007 and f-014 are not a genuine two-sided disagreement about whether R3 is too strict or too loose — they are describing two different axes of the same rule, and only one of the two diagnoses survives contact with the code.
  - R3's actual behavior, verified: `status: confirmed` requires zero fields in state `drafted` (line 199-205). It does **not** require fields to be `confirmed` — `declined` also clears the check. f-007's literal description ("forces all five fields to reach declined-or-confirmed... no partial-confirm state") is accurate as a state-machine fact: `status` is a card-level binary (`provisional`/`confirmed`, line 126-129), so there is genuinely no way to represent "3 of 5 resolved" as a distinct status value.
  - But f-007's causal claim — that this rigidity is in tension with ruling 12's gradual-adoption rationale — misapplies ruling 12, which is stated as a **project-level rollout** rule ("backfill on first touch, never bulk," about *when across 82 projects* a card gets touched) not a **field-level** rule about how much of one card must resolve before its status flips. Nothing in ruling 12's text as quoted in the proposal addresses within-card granularity.
  - More importantly, f-007's own source lens (`fd-hci-ratification-cost`) states as an axiom that "all-or-nothing approval gates... are prone to end-of-session fatigue and rubber-stamping" — and that is exactly the mechanism f-014 caught in the act: `declined` requires only a `reason` and a `needs` string (line 172-179), no evidence, no scope check, nothing that distinguishes "I genuinely don't know" from "I am declining this to get through the gate." Five short strings and a self-attested `confirmed_by` clear R3 and R4 (R4 only fires `if line:`, and a card can simply leave `line` unset) and the validator exits 0 — the sole silent-permit code the plan gate checks. f-007 predicted the rubber-stamp risk; f-014 found where it actually lives — not in a hypothetical "forced to confirm five things" fatigue spiral, but in the `declined` branch's total absence of a cost floor.
  - So f-007's remedy direction (loosen R3, add a partial-confirmed state) would not fix what f-014 found and could make it harder to see: a "partially confirmed" status is itself gameable the same way (decline the rest, claim partial credit for the remainder) and adds a state that needs the same integrity scrutiny R3 currently lacks. The fix that addresses both findings at once is the opposite move — leave R3's "no field left drafted" requirement alone (it's doing real work: forcing every field to be *touched*), and instead raise the cost of the `declined` branch itself, e.g. require ≥1 field to reach `confirmed` (not merely non-drafted) before `status: confirmed` is legal, or require `declined`'s `needs` to cite a concrete blocker the way `drafted` must cite evidence (R1). That closes f-014's hole without reopening the door f-007 worried about — a genuinely partial card just stays `provisional`, visibly, which is what ruling 11's ranking already expects.
- **Evidence:** `validate()` line 197-209 (`drafted = [n for n in FIELDS if states[n] == "drafted"]` — only checks for the string `"drafted"`, `"declined"` is invisible to this check); line 172-179 (declined branch requires only truthy `reason` and `needs`, no evidence list, no scope); brainstorm ruling 12 as quoted in the proposal is phrased entirely in terms of estate-wide backfill timing, never per-card field granularity; `fd-hci-ratification-cost` lens axiom 3 ("All-or-nothing approval gates... are prone to... rubber-stamping") independently predicts f-014's exploit rather than supporting f-007's fix.
- **Suggestion:** Keep R3's "no drafted fields" requirement as-is; add a floor requiring at least one field to reach `confirmed` (not just non-`drafted`) before `status: confirmed` validates, and/or require `declined`'s `needs` field to name a concrete unblocking condition rather than any non-empty string, so the cheap escape f-014 found can't be exercised as a five-line rubber stamp.

### plan-gate-blind-to-strength
- **Severity:** P1
- **Where:** `dotfiles/common/.claude/hooks/guard-plan-needs-card.sh:75-83` (the `case "$CODE" in` block)
- **What:** The reconciliation above matters more than a documentation nitpick because the exploit it describes doesn't stop at `card-check.py`'s JSON output — it reaches the actual plan-write permit. `guard-plan-needs-card.sh` branches purely on the process exit code (`0) exit 0 ;;` — "the only silent permit," per its own comment); it never reads or thresholds on `strength.score`, which is the only field in the JSON payload that would distinguish a card confirmed with real content from a card confirmed by declining all five fields. Both produce exit code 0, and both silently permit a plan write with no advisory printed (advisories only fire on codes 1/2/3, or when an override is used). A hollow-declined card is therefore not just a scoreboard artifact for the future TUI ranking (where `strength.score` would at least visually rank it near the "absent" end) — inside this goal's own DONE WHEN clause ("the plan gate has been observed permitting a real plan... and refusing one into a repo without a card"), the permit path and the hollow-decline path are indistinguishable to the one enforcement point that exists today.
- **Evidence:** `guard-plan-needs-card.sh` lines 75-83 switch only on `$CODE` from `card-check.py`'s exit status; the script never invokes `--json` or parses `strength`. Cross-checked against `card-check.py:255-273` (`emit()`), which does compute `strength(card)` for the JSON path but that computation is dead weight from this gate's perspective since the gate never asks for `--json`.
- **Suggestion:** Either accept this as a known, logged gap (declined-everything is not free — it requires an agent or mk to deliberately write five hollow entries, which is a smaller and more visible surface than the free-text `AUTARCH_CARD_OVERRIDE` escape hatch already flagged), or have the gate consult `--json` and refuse (or advise) when `strength.confirmed == 0` on an otherwise-confirmed card, so the one enforcement point that matters treats "confirmed, hollow" differently from "confirmed, real."

## Verdict
The contradiction resolves in f-014's favor: R3's all-or-nothing *form* (every field must leave `drafted`) is real but not the problem, because the `declined` branch gives every field a costless escape from that requirement — so the rule that looks strict on paper is permissive in practice, and f-007's proposed fix (loosen it further with a partial-confirmed state) would not close that gap and could normalize it further. The one new fact this reconciliation surfaces is that the gap isn't confined to the future TUI's `strength.score` display — `guard-plan-needs-card.sh` enforces on exit code alone, so the hollow-confirm path already reaches the actual plan-write permit today, before any TUI exists to show the difference.
