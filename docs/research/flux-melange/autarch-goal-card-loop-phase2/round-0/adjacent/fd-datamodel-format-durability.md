## Findings

### strength-line-synthetic-bump-contradicts-ruling-11
- **Severity:** P1
- **Where:** `dotfiles/common/.local/bin/card-check.py:217-238` (`strength()`), read against ruling 11 in `docs/brainstorms/2026-08-13-autarch-universal-interface-brainstorm.md` (decisions table row 11) and the proposal's DONE WHEN ("ranking matches ruling 11 against real card strengths").
- **What:** `strength()` counts `counts["confirmed"]` from the five `FIELDS` (`persona, pain, cuj, success, guardrail`) by their per-field `state`, exactly as ruling 11 specifies. Then it adds a sixth, unconditional bump: `if card.get("line"): counts["confirmed"] += 1`. But `line` is a bare top-level string, not a field with its own `drafted/declined/confirmed` state (R4 only requires that persona and pain both be **non-declined**, i.e. `drafted` is enough) — an agent drafter can set `line` unilaterally the moment it drafts persona+pain, with `status: provisional` and zero fields mk has touched.
- **Evidence:** Ruling 11's own stated rationale, quoted verbatim from the brainstorm: *"Only `confirmed` fields count toward strength — if drafted counted, running the drafter across 82 projects would look like progress and quietly reorder the door."* Yet a fully-provisional, drafter-only card with `line` set scores `strength.score = 1, of: 6` — a real, non-zero score derived entirely from unconfirmed drafter output — which is precisely the "drafted looks like progress" failure ruling 11 names. Verified by tracing `strength()`: the `line` bump path is reached independently of every field's `state`, including when all five are `drafted`.
- **Suggestion:** Either (a) exclude `line` from the strength numerator entirely and report `of: 5`, or (b) only count `line` toward strength when the card's overall `status == "confirmed"` (so the bump tracks mk's ratification, not the drafter's derivation). Fix in `strength()` before phase 2 wires `card-check.py --json` into the TUI's ranker — the DONE WHEN clause "ranking matches ruling 11" cannot be verified true while this contradiction sits in the scoring function it depends on.

### invalid-state-undocumented-in-format-reference
- **Severity:** P1
- **Where:** `docs/reference/product-card-format.md` (`git show 38715de:docs/reference/product-card-format.md`), closing section "Absent, provisional, confirmed"; contrasted with `card-check.py:43` (`CONFIRMED, PROVISIONAL, INVALID, ABSENT = 0, 1, 2, 3`) and the proposal's DONE WHEN clause "a project whose card is absent, provisional, invalid and confirmed are four visibly distinct row states."
- **What:** The format reference's own closing taxonomy names exactly three states a card can be in — Absent, Provisional, Confirmed — with one sentence each on what causes them and what the gate does. It never mentions `invalid` as a state a human or the TUI needs to recognize, despite `card-check.py` treating "exists but does not parse, or violates a hard rule" as a categorically distinct 4th verdict (explicit in the module docstring: *"'absent' and 'invalid' must never share an exit code... 'there is a card and it is malformed' is a defect"*).
- **Evidence:** Read side by side: the format doc's authoritative state model is 3-valued; the validator's and the DONE WHEN's is 4-valued. Nothing in `product-card-format.md` tells a TUI author (or mk, reading the doc to understand what they'll see) what an invalid card looks like, what causes it beyond "R1-R4 violated," or how it should render differently from provisional. Whoever builds the phase-2 row-state rendering has to reverse-engineer "invalid" from `card-check.py`'s error strings rather than from the format spec that is supposed to be normative.
- **Suggestion:** Add a fourth bullet to "Absent, provisional, confirmed" (rename the section "Absent, provisional, invalid, confirmed") stating what invalid means for a human reading a row — at minimum, that it means "a card exists but the validator's exit-2 message names which R1-R4 rule it broke," and whether the TUI is expected to surface that message text or just a color. Cheap now; the DONE WHEN clause names this exact 4-state requirement, so the spec gap should close before, not during, TUI implementation.

### cuj-confirmed-with-no-ref-or-path-validates-clean
- **Severity:** P2
- **Where:** `dotfiles/common/.local/bin/card-check.py:139-183` (the per-field validation loop in `validate()`).
- **What:** For every field except `cuj`, `confirmed` and non-evidence-required `drafted` states are checked for a `value` (`if name != "cuj" and not spec.get("value")`). `cuj` is explicitly exempted from that check because it identifies via `ref`/`path` instead of `value` — but nothing anywhere in the loop ever reads `spec.get("ref")` or `spec.get("path")` for any state. A card with `cuj: {state: confirmed}` and no other keys passes R1 (no evidence required once state isn't `drafted`), passes the value check (exempted), and passes R2 (cuj isn't in `SCOPED_FIELDS`). Exit code 0.
- **Evidence:** Confirmed by reading the full `FIELDS` loop (`card-check.py:140-183`) line by line — there is no `ref`/`path` presence check reachable from any branch, for `drafted`, `declined`, or `confirmed`. This contradicts `product-card-format.md`'s own worked example, which shows `cuj.ref` and `cuj.path` as the field's actual identifying content (*"`cuj.ref` may be null... `path` alone identifies the journey"* — implying at least one of the two is expected to be present, not that both may be absent).
- **Suggestion:** Add a check requiring `path` (the one field the format doc says is never optional — only `ref` may be null) when `cuj.state in ("drafted", "confirmed")`. Frame as a question for the format author, per this lens's own uncertainty convention: is a confirmed CUJ reference with neither `ref` nor `path` actually meant to be legal — e.g. as a way to say "this project has no journey but I'm ratifying that anyway" — or is this an oversight in the field-loop's `cuj` exemption bleeding further than intended?

### card-version-pinned-no-migration-story
- **Severity:** P3
- **Where:** `dotfiles/common/.local/bin/card-check.py:118-121`; `docs/reference/product-card-format.md` header (`**Version:** 1`) and YAML example (`card_version: 1`).
- **What:** `card_version` must equal exactly `1` — any other value, including a future `2`, raises `CardError` and the card is `invalid`. Neither `product-card-format.md` nor `card-drafter.md` describes what happens when the format needs to change: no versioned-field-set story, no note on whether `card-check.py` will support reading old and new versions side by side, no pointer to where a migration would be written.
- **Evidence:** Grep of both reference docs for "migrat" and "version" surfaces only the single pinned value; the lens's own domain experience (v1 schemas hardening before a second consumer arrives) applies literally here — `pkg/tui` is the second reader this proposal is about to add.
- **Suggestion:** Not urgent to fix now — zero cards exist in any repo yet, so the cost of a future migration is still near its floor. Worth one sentence in `product-card-format.md` (e.g. "a `card_version` bump requires updating `card-check.py`'s accepted set and re-validating every existing `docs/why.md`") so the constraint is at least named before cards start accumulating.

## Verdict
The format's schema and validator are internally coherent on the paths that get exercised by drafting and gating, but two gaps sit exactly where the proposal's own DONE WHEN clauses point: the ranking function silently rewards unconfirmed drafter output in a way ruling 11 explicitly forbids, and the fourth row-state the TUI must render has no definition in the document that is supposed to be normative for it. Both are cheap to fix now, before phase 2 reads either.
