## Findings

### depends-on-paths-absent-from-local-checkout
- **Severity:** P0
- **Where:** proposal frontmatter `depends_on:` (product-card-format.md, card-drafter.md, card-drafter-measurement.md, cited at commit `38715de`); Autarch local `main` (HEAD `7c02ffd`)
- **What:** None of the three Autarch-side `depends_on` paths exist anywhere in the local working tree. The commit the proposal and its "What already shipped" section cite as having landed them, `38715de`, is **not an ancestor of local `main`** — it exists only on `origin/main` (and as a loose object reachable by direct SHA, which is how this review recovered the content at all, via `git show 38715de:<path>`). Local `main`'s copy of the brainstorm is a *different* commit (`7c02ffd`, diverged from `origin/main`'s `1e57bab`/`38715de` at the same parent `0d8728c`), and it has only a "Key Decisions" table numbered 1-10 plus an "Open Questions" list still carrying items unresolved — including item 3, "Backfill policy for 82 projects... Draft cards for all of them at once, or only on first touch?", the exact question the proposal cites as settled by "ruling 12." The proposal names "Autarch's local `main` divergence" in its own OUT list, but scoping it OUT does not make the DONE WHEN clauses that depend on these files resolvable from the checkout the goal will actually run in.
- **Evidence:** `find /Users/sma/projects/Sylveste -iname "*product-card-format*"` (and `*card-drafter*`, `*card-drafter-measurement*`) → no results; `git -C Autarch merge-base --is-ancestor 38715de HEAD` → not an ancestor; `git -C Autarch branch -a --contains 38715de` → `origin/HEAD`, `origin/main` only; local `docs/brainstorms/2026-08-13-autarch-universal-interface-brainstorm.md` (151 lines): `## Key Decisions` rows 1-10 only, `## Open Questions` items 1-8 still listed, item 3 unresolved.
- **Suggestion:** Fast-forward or merge local Autarch `main` to include `38715de` (or explicitly re-scope the goal to run from `origin/main`/a worktree that has it) before any other step in this goal starts. Only then does "the confirm-step cost and format findings are written into the brainstorm as rulings" target a brainstorm file that actually has rulings 11-13 to append to.

### tui-coverage-fraction-scoped-to-sessions-not-estate
- **Severity:** P1
- **Where:** proposal DONE WHEN: "the TUI renders all 21 sessions as project rows with a stated coverage fraction"; brainstorm Open Question 6 ("The 1-of-21 blindness"); "The estate this is aimed at" section (82 projects)
- **What:** "21" is the count of currently-attached tmux sessions (per Open Question 6, replacing intermux's undisclosed 1-of-21 blindness), not the count of projects in the estate (82). A coverage fraction stated as "N of 21" reads as healthy — plausibly near 100% — while staying silent on how many of the estate's 82 projects have a card at all, since only projects with a currently-live session appear as rows in phase 2 in the first place. The instrument this goal exists to replace (intermux reporting 1 of 21 and disclosing no gap) is being replaced by a door that can legitimately report "21 of 21" while covering roughly a quarter of the estate the whole proposal is diagnosed against.
- **Evidence:** proposal DONE WHEN, verbatim: "the TUI renders all 21 sessions as project rows with a stated coverage fraction"; brainstorm decision 9: "All 21 sessions are already on one server"; "The estate this is aimed at" section: "82 projects, 2,270 plans... 0 metrics."
- **Suggestion:** State the coverage fraction against the estate's true project count (82, or whatever it is at run time), not 21, or carry both numbers in the row so "sessions with cards" and "estate projects with cards" are never collapsed into one figure.

### read-path-deferred-past-the-phase-that-justifies-it
- **Severity:** P1
- **Where:** proposal sequencing (confirm unc-rancher, then build phase 2); brainstorm decision 9-10 (tmux switch-client attach, phase 1 explicitly "no UI"); `product-card-format.md` intro ("It is read three ways: by mk at a glance in a switcher row...")
- **What:** The stated mechanism by which a why-card gets read at all — as opposed to joining 2,270 unread plans — is the switcher row itself: mk hits the door via `tmux switch-client` and the card is compressed into a glanceable line before anything else happens. Confirming unc-rancher's card first, with no TUI row rendering it, means the confirm step and its format findings ("are these the right six fields?") are produced by mk reading a page-length YAML+prose file directly in an editor — the opposite of the read-path the design is betting on. The goal risks writing a ruling about six-field format adequacy from an encounter with the format the shipped design will never actually offer a user.
- **Evidence:** proposal text: "Draft its `docs/why.md` per the drafter procedure, then mk confirms it"; brainstorm decision 9 (tmux switch-client) and decision 10 (phase 1 "no UI"); `product-card-format.md`: "It is read three ways: by mk at a glance in a switcher row, by an agent before it writes a plan, and — for slate items — by a stranger deciding whether to fund it."
- **Suggestion:** If confirm-then-TUI ordering stands, have mk confirm the card twice — once cold as currently planned, and once after seeing it compressed into a mocked or hand-built single TUI row — and record whether the format finding changes between the two reads, since the row is the read-path the ruling is meant to future-proof.

### no-appraisal-state-for-parked-projects
- **Severity:** P1
- **Where:** `product-card-format.md` §"Absent, provisional, confirmed" (three states only); Autarch `CLAUDE.md` §Overview (lists Coldwine, Pollard); brainstorm "Key Decisions" row 8 ("Coldwine and Pollard parked")
- **What:** The card format recognizes exactly three project-level states — absent, provisional, confirmed — with no state for "appraised and intentionally not being described." Coldwine and Pollard are real, named tools in this repo's own `CLAUDE.md` that decision 8 has already parked, and the proposal's own OUT list separately excludes "reviving Bigend, Coldwine or Pollard." Under ruling 11's ordering, a parked project with no card scores identically to a live, simply-neglected project (absent, strength 0) — the door cannot distinguish "retired by decision" from "nobody has gotten to it yet," so parked tools compete for the top-of-list attention slot ruling 11 reserves for the estate's most neglected active work.
- **Evidence:** `product-card-format.md` §"Absent, provisional, confirmed" — three bullets, no fourth; Autarch `CLAUDE.md` §Overview lists Coldwine ("Task orchestration + sprint runs") and Pollard ("General-purpose research intelligence") as current tools; brainstorm "Key Decisions" row 8: "Bigend and Gurgeh in, Coldwine and Pollard parked."
- **Suggestion:** Add a fourth, project-level state (e.g. `parked`, set by reference to a decision doc rather than a drafted card) that ruling 11's ranker excludes from "weakest card first," so appraisal decisions already on record (decision 8) are visible to the ranker instead of only to a human who has memorized the brainstorm.

### no-reappraisal-cadence-on-confirmed-cards
- **Severity:** P2
- **Where:** `card-check.py` R3 (lines 206-209, requires `confirmed_by`/`confirmed_at`); `product-card-format.md` §"Card status"
- **What:** `confirmed` is not attester-free — R3 does require both `confirmed_by` and `confirmed_at`, so the state is reproducible in the narrow sense of naming who and when (correcting any assumption that it carries no attester at all). What is genuinely absent is any expiry, `superseded_by`, or reappraisal trigger: a card confirmed against today's unc-rancher carries the identical visual weight in six months, after the code underneath it has moved, as one confirmed this morning. Nothing in `card-check.py`, the gate, or the DONE WHEN clauses distinguishes a confirmation that is still true from one that has quietly become an assumption.
- **Evidence:** `card-check.py:206-209` (`confirmed_by`/`confirmed_at` required; no expiry or supersede field checked anywhere in `validate()`); `product-card-format.md` §"Card status" describes only the drafted→confirmed transition, no revisit condition.
- **Suggestion:** Not blocking for this goal's single-card test; before ruling 12 scales confirmation to 82 projects, add an optional `reappraised_at`/`superseded_by` pair the ranker can use to visually distinguish a stale confirmation from a fresh one.

## Verdict
The instrument's own dependency chain is unverifiable from the checkout it will run in — fix that before anything else in this goal executes. Once fixed, the design still counts and orders a subset (21 live sessions) while implicitly claiming to answer for the estate (82 projects), tests the format's adequacy before the read-path meant to make cards get read exists, and has no state for a project already appraised and parked by name in this repo's own decisions.
