## Findings

### ranking-clause-vacuous-at-n1
- **Severity:** P0
- **Where:** `docs/proposals/2026-08-13-goal-card-loop-phase2.md:41-44` (ordering paragraph), `:55` (DONE WHEN "ranking matches ruling 11 against real card strengths"), `:46-48` (OUT: "backfilling cards beyond the one confirmed")
- **What:** Ruling 11's order is a strict three-tier lexicographic sort — funded, then pins, then weakest-card-first by `strength.score`. `unc-rancher` is explicitly funded (proposal line 24: "a real GSV games-slate item"), which places it in tier 1, where position is governed by the funding mechanism, not by card strength. `strength.score` only does ordering work inside tier 3, the unfunded/unpinned tail. OUT caps this goal at exactly one confirmed card and forbids drafting any others, so at completion every one of the other 81 projects is card-absent — `strength()` in card-check.py returns `score: 0` for all of them (see the emit() finding below), tied. There is therefore no state reachable under this goal's own scope in which two real, differently-scored cards exist to compare. The DONE WHEN clause "ranking matches ruling 11 against real card strengths" can be satisfied by unc-rancher sitting at the top of the funded tier — true whether its card were absent, provisional, invalid, or confirmed — and by 81 tied zeros filling tier 3 in arbitrary order. The one mechanism ruling 11 actually introduces (rank the tail by how much of its why is real) is never exercised by real data, in a goal whose stated purpose is to "answer the question one real card raises."
- **Evidence:** Ruling 11 text (brainstorm, "funded first, then pins, then weakest card first"); proposal `:41-44` restates the same tiering and names `strength.score` as the tail's sort key only; proposal `:46-48` OUT list bars backfilling beyond the one card; `card-check.py:255-267` `emit()` gives absent cards `strength: {"score": 0, ...}` by construction (see next finding for INVALID too).
- **Suggestion:** Either narrow the DONE WHEN clause to what it can actually verify ("unc-rancher renders in the funded tier, regardless of score"), or widen the goal's real-data floor: confirm (or at minimum draft, non-bulk, on organic first-touch) a second project outside the funded tier before claiming the tail-ordering mechanism has been checked against anything but zeros.

### mycroft-turn-collision-unexamined
- **Severity:** P1
- **Where:** Brainstorm ruling 12 ("backfill on first touch, never bulk"); `dotfiles/common/.claude/hooks/guard-plan-needs-card.sh` (global PreToolUse matcher on `docs/plans/*.md`, ruling 5's "fires whether or not the door is open"); `Sylveste/apps/Autarch/CLAUDE.md` Overview — Mycroft is described as "Fleet orchestrator — escalating autonomy (T0 observe → T1 suggest → T2/T3 auto-dispatch)" with `mycroft run`/`mycroft promote`/`mycroft tier` CLI already shipped in the same repo this proposal lives in.
- **What:** Ruling 12 deliberately rejects bulk drafting and relies on "first touch" as the sole trigger, reasoned as a per-project, mk-paced event. But neither the proposal nor the brainstorm mentions Mycroft — a fleet component in the *same monorepo*, already capable of T2/T3 auto-dispatch, i.e. autonomously assigning agents to work across multiple projects without a human in the loop per dispatch. If Mycroft (or any future autonomous batch operation) dispatches agents into several repos in one patrol cycle and more than one of those agents reaches its own first `docs/plans/*.md` write in the same window, `guard-plan-needs-card.sh` fires independently and synchronously in each session — there is no queue, no coalescing, and no signal anywhere in this design that groups simultaneous demands into one confirm sitting for mk. The result is bulk-shaped demand arriving through an on-demand trigger that was specifically designed to avoid bulk. This is exactly the "turn 2 through turn 82" question the goal never asks: whether the loop degrades under concurrent, agent-initiated (not mk-initiated) first touches, which is a live capability of this codebase, not a hypothetical.
- **Evidence:** Ruling 12's own stated rationale is anti-bulk; the gate is global and per-write-event with no batching logic (`guard-plan-needs-card.sh:37-47` matches and roots independently per file write); Autarch `CLAUDE.md` Mycroft description confirms auto-dispatch is a shipped capability, not a future one.
- **Suggestion:** State explicitly, even if only as an open question added to the brainstorm, whether Mycroft-initiated (or any autonomous multi-repo) dispatch is in scope for the card gate, and if so what happens when N first-touches land in the same session — coalesce into one confirm batch, defer non-blocking, or accept N independent BLOCKs. Silence here is itself the finding; do not let a reasonable default get inferred without being written down.

### confirmed-has-no-expiry
- **Severity:** P1
- **Where:** `dotfiles/common/.local/bin/card-check.py:197-209` (R3 ratified block); `guard-plan-needs-card.sh:76-77` (`0) exit 0 ;;  # confirmed -- the only silent permit`)
- **What:** Once `status: confirmed`, `card-check.py` returns exit 0 permanently. `confirmed_at` is checked only for presence (`if not card.get("confirmed_at"): raise CardError(...)`, line 208) — never for recency, and nothing anywhere (validator, gate, or the proposal's DONE WHEN) revisits a confirmed card as the underlying repo's actual persona/pain/success drift out of date. Ruling 12 commits the estate to running this loop 82 times, but the design says nothing about whether a confirm is a one-time event or a periodic one. A subak's rotation schedule exists precisely because a right granted once and never reviewed drifts out of sync with which field actually needs water this season; this format has the granting half of that pattern (R3 ratified) and none of the review half.
- **Evidence:** `card-check.py:181-209` full confirmed-state validation — no date arithmetic, no comparison against a re-confirmation window. Ruling 12 text carries no recurrence clause. This goal's own DONE WHEN asks only that unc-rancher's card exit 0 once, which the mechanism above shows is permanent by construction.
- **Suggestion:** Either add explicit unstaleness to the brainstorm as a ruling (e.g., "a card is never re-checked; treat this as accepted" is a legitimate answer) or record it as open question 9. Don't let "confirmed" silently mean "confirmed forever" without that being a decision someone made on purpose.

### override-priced-against-nothing
- **Severity:** P1
- **Where:** `docs/proposals/2026-08-13-goal-card-loop-phase2.md` DONE WHEN, clause "the confirm-step cost and any format findings are written into the brainstorm as rulings with reasons"; `guard-plan-needs-card.sh:84-91` (OVERRIDE block — any non-empty `AUTARCH_CARD_OVERRIDE` string is sufficient, logged, always permits, checked *after* the verdict).
- **What:** This goal's explicit deliverable is a real number: how many minutes a genuine confirm sitting costs mk on unc-rancher. That number becomes the input ruling 12 is judged against for turns 2 through 82. But the override that bypasses the entire gate costs whatever it takes to type one non-empty string into an env var — no minimum content, no field engagement, nothing checked against the six slots. The moment this goal publishes "confirming costs N minutes," it has also published the exact number that makes overriding N minutes cheaper for every one of the other 81 turns, and nothing in this goal's scope tracks override *rate* going forward to know whether that prediction is happening. The goal measures the cost of the front door and is silent on traffic through the window it also documents.
- **Evidence:** `guard-plan-needs-card.sh:19-23` module comment states the override policy plainly ("Overrides are logged, never forbidden... An override with no reason is not an override"); the proposal never mentions `AUTARCH_CARD_OVERRIDE` by name and DONE WHEN contains no clause about override frequency or a threshold at which override use would itself be a signal that the loop has failed.
- **Suggestion:** Add a companion metric alongside "confirm-step cost in minutes": an intent to grep `hook_log_warn "guard-plan-needs-card" "OVERRIDE..."` entries at some future checkpoint (e.g., after turn 10 or turn 25) and compare override count to confirm count. This doesn't need to happen in this goal — it needs to be a named future checkpoint so the estate isn't 82 turns in before anyone looks.

## Verdict
The proposal's real exposure is not that the loop will be misused but that its one exercised turn cannot generalize the two things ruling 11 and ruling 12 actually depend on: a comparative score-ordering (unc-rancher's funded-tier position makes the tail-sort mechanism untested by construction) and a recurring cadence (nothing in the code or the rulings says what happens on re-touch, at scale, or under autonomous concurrent demand from Mycroft — a capability that already exists in this repo and this brainstorm never names). None of these four findings block landing turn 1; all four are cheap to write down as explicit open questions or checkpoints before ruling 12 is trusted for turn 82.
