## Findings Index

- [P1] second-reader-has-no-prose-signal-at-all — the `--json` contract carries no field marking prose present/absent/length, so the TUI (second consumer) cannot even detect the gap the validator is blind to, let alone re-derive a rule for it (§Shape)

## Findings

### prose-body-invisible-to-validator-confirmed
- **Severity:** P1
- **Where:** `dotfiles/common/.local/bin/card-check.py:55-70` (`split_frontmatter`), `:278-286` (`main`, the only two places `text` is touched), cross-checked against `dotfiles/common/.claude/hooks/tests/test-card-check.sh:68-107` (`write_confirmed_card`, the suite's baseline fixture) and `:356-381` (`test_confirmed_with_all_declined_is_allowed`).
- **What:** CONFIRMED, and more strongly than the prior finding states. `split_frontmatter` returns only `lines[1:i]` — the block strictly between the opening and closing `---` — and `main()` passes that block to `load_yaml`/`validate` and never touches `text` again. There is no code path anywhere in the file that inspects a single byte after the closing delimiter. This isn't circumstantial: the test suite *demonstrates* it directly. `write_confirmed_card`, the fixture every other test in the suite is built from, appends a literal `Prose body.` after the closing `---` (line 105) — showing the format's intended shape does include prose. But `test_confirmed_with_all_declined_is_allowed` (lines 356-381) writes a card whose heredoc ends *at* the closing `---` with no trailing content at all — zero prose, not even a blank line — and asserts `rc == 0` (confirmed). The validator's own test suite proves, on the record, that `status: confirmed` is reachable with an absent prose body.
- **Evidence:** `split_frontmatter` (lines 55-70) returns `"\n".join(lines[1:i])` and raises only if the block never closes; nothing downstream receives `lines[i+1:]`. `main()` (lines 278-296) calls `load_yaml(split_frontmatter(text))` once and reports verdicts purely off the parsed `card` dict — `text` itself goes out of scope unused after that call. `test_confirmed_with_all_declined_is_allowed` writes a card ending in `decisions: []\n---\nCARD` (heredoc closes immediately after the delimiter) and its only assertion is `[[ "$rc" == "0" ]]`.
- **Caveat on the doc-side half of the original claim:** I could not verify the specific sentence attributed to `product-card-format.md §Shape` ("the prose body is exactly what the funding page renders as sales copy for unc-rancher") — that file does not exist anywhere in the local `~/projects` tree (searched, zero hits), consistent with the already-established fact that none of the proposal's `depends_on` documents resolve locally. What the locally-readable proposal text supports is weaker but points the same direction: "[unc-rancher's] card is also the funding page's sales copy, which is the coupling this design rests on" (proposal, line 24-25) — it says the *card* is sales copy, without the proposal itself distinguishing frontmatter fields from prose. The mechanical half of the claim (validator blind to prose; confirmed reachable with none) is proven directly from code and tests. The attribution half (what the absent format doc specifically states about prose vs. sales copy) is not verifiable from what exists on disk and should not be asserted as read.
- **Suggestion:** N/A — this is the confirmation entry, not a new proposed fix. See the following two findings for what to do about it.

### second-reader-has-no-prose-signal-at-all
- **Severity:** P1
- **Where:** `card-check.py:255-273` (`emit`, the entire `--json` payload shape) and `:217-238` (`strength`).
- **What:** Once a second consumer exists (the phase-2 TUI, and per the proposal's own framing, eventually the funding page), it will need to know something about the prose body — at minimum whether unc-rancher's card *has* sales copy before rendering or linking to it. But the JSON contract the validator emits — `verdict`, `code`, `card` (a path string), `reason`, `notes`, `strength` — carries no field for prose presence, prose length, or a byte offset into the file. This is a sharper version of the lens's usual worry ("a second reader re-derives a rule the validator enforces procedurally"): here there is no rule to re-derive, procedural or otherwise. Any future reader that cares about prose has to open and re-parse the raw file itself, using a *second, independent* frontmatter-splitting implementation that must stay byte-for-byte consistent with `split_frontmatter`'s exact rules (first-line `---` requirement, first-match-wins closing delimiter) or it will disagree with the validator about where the card ends and the sales copy begins.
- **Evidence:** `emit()` (lines 255-273) constructs the entire JSON payload from `verdict`, `code`, `str(path)`, `reason`, `notes`, and `strength(card)` — every one of those is derived from the parsed frontmatter dict or the validator's own control flow; none derives from or references `text[closing_delim_line:]`. `strength()` (lines 217-238) likewise only ever reads `card.get("fields")` and `card.get("line")`.
- **Suggestion:** Before pkg/tui exists, add a cheap, procedural signal to the JSON contract — e.g. `"prose_present": bool` or `"prose_len": int`, computed once in `main()` right where `split_frontmatter` already knows the closing-delimiter line index — so a second reader can ask the validator "is there sales copy back there" instead of re-implementing frontmatter-splitting to find out. This is a few-line addition to a function that already has the line index in hand, not a rewrite.

### canonical-fixture-normalizes-decorative-prose
- **Severity:** P2
- **Where:** `dotfiles/common/.claude/hooks/tests/test-card-check.sh:68-107` (`write_confirmed_card`), and the full 30-assertion run list at `:690-720`.
- **What:** `write_confirmed_card` is the shared baseline every positive-path test in the suite mutates from (`test_confirmed_card_passes`, both R2 scope tests, the R3/R4 tests, the strength tests — at least a dozen call sites). Its prose body is exactly one throwaway line, `Prose body.`, and not one of the 30 assertions in the suite (nor, per the proposal's own count, any of the 30 mutations) ever inspects, hashes, or length-checks that line. Combined with the first finding — a fully prose-absent card also validates — the suite has no test anywhere that would fail if a future edit to `card-check.py` (or to the card-writing tooling) silently truncated or dropped prose across every card in the estate. That is exactly the "expensive to discover only after the TUI reads the format" scenario the north-star question asks about: it would surface as a blank sales-copy panel in the TUI/funding page, not as a red suite.
- **Evidence:** Grep of `test-card-check.sh` for any assertion referencing "Prose body" or a body/prose-adjacent variable name returns nothing; the 30 registered test functions (lines 690-720) are exclusively named after frontmatter rules (R1-R4, verdict separation, strength).
- **Suggestion:** Once the `prose_present`/`prose_len` field from the prior finding exists, add one cheap suite assertion pinning it against the baseline fixture (e.g., `write_confirmed_card` should report `prose_present: true`, and a hand-truncated variant should report `false`) — this is the regression tripwire the current suite is missing, not a new subsystem.

## Verdict
The prior finding is CONFIRMED on its mechanical claim, and confirmed more strongly than stated: the test suite itself contains a passing, intentional case (`test_confirmed_with_all_declined_is_allowed`) of a `status: confirmed` card with literally zero prose. Its attribution to a specific sentence in `product-card-format.md §Shape` could not be independently checked because that file is not present anywhere in the local tree — treat that half as unverified, not confirmed. The durability risk this creates is real and current-day: the phase-2 TUI (and, per the proposal's own framing, eventually the funding page) has no procedural signal to key off for "does this card have sales copy," and the test suite has no tripwire that would catch prose silently going missing.
