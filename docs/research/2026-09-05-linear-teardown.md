# Linear teardown: from project context to delegated work

## Lineage and evidence

The user redirected the reference research:

> what about Linear and other project/roadmap/portfolio management/execution applications?

Linear is now an explicit reference. A structured probe about its appeal led
the user to clarify the whole intended experience: a one-stop working
environment for their product-management practice, with increasingly autonomous
engineering agents that apply their judgments and push back when something is
missing. The [governing ruling](2026-09-05-foundation-sprint-questions.md#governing-direction-the-product-managers-working-environment)
is recorded verbatim. Specific Linear preferences and experienced friction
remain open; this analysis is not testimony about the user's Linear workflow.

## Reconstructed journeys

These are sequences assembled from documentation, not completed live tasks.

1. **Orient and drill down.** Open Initiatives, inspect a health indicator,
   read the update explaining it, and enter a contributing project. Read its
   overview before opening the issues. Autarch mapping: daily walk, steps 1–5.
2. **Connect intent to a piece of work.** Open the project overview, add or
   consult a resource, inspect milestones, then work with issues while retaining
   access to project details. Autarch mapping: canon tending, steps 1–2, and
   session dive, steps 2–3. Foundation approval is an Autarch requirement;
   resource presence alone does not supply it.
3. **Delegate and follow through.** Open an issue, choose an agent, retain
   human ownership, and follow delegated work through issue views and activity.
   Alternatively open the issue in a coding tool with its context. Autarch
   mapping: session dive, steps 4–6. Launch and returned evidence need separate
   proof in Autarch's Clavain integration.

## Choice → tradeoff → Autarch implication

The costs and implications here are analyst inferences to test with the user.
The governing question is how these mechanisms support ongoing human product
judgment and agent follow-through, including a reasoned challenge to a prior
decision.

| Linear choice | Benefit and cost | Candidate Autarch implication |
|---|---|---|
| Context-rich overview plus details accessible during issue work | Helps move between intent and execution; important context can still be buried in prose or unopened resources. | Keep the relevant mission, persona, CUJ, and decision accessible from the active work item. Do not equate having a document with having an agreed foundation. |
| Curated initiatives alongside filtered views | Distinguishes deliberate commitments from automatic collections; users must understand which kind of grouping they are seeing. | Keep a chosen roadmap distinct from a view of whatever happens to be active. |
| Health signal backed by a dated narrative | Makes exceptions scannable and explainable; someone must maintain the assessment, and stale prose can mislead. | Let Flere prepare a source-cited change brief; show missing or old evidence explicitly. Human assessment and observed execution state remain distinguishable. |
| Project-only timeline | Makes broad sequencing legible; issue-level blockers require a deeper view. | Compare a roadmap of outcomes with execution details reached by drilling in. Dates should reflect actual certainty. |
| Human assignee plus agent delegate | Keeps accountability visible; it adds two roles whose meaning must be clear. | Show who requested or owns the outcome separately from Flere and any Clavain execution agents. |
| Shared and team agent guidance | Makes context reusable; receiving instructions does not prove compliance. | Show inherited guidance, local rulings, and the context passed into execution. Clavain's policy enforcement remains a separate responsibility. |

## The vocabulary mismatch matters

Linear's project is usually a finite effort. Autarch's project is an enduring
garden such as Autarch or Flere, with its own mission and a succession of
efforts. Copying the name without that distinction would make the workbench
ambiguous before its first sprint.

An unresolved model worth discussing is an enduring project with foundations,
an outcome roadmap, and bounded efforts that contain Clavain sprints and work
items. This is a hypothesis, not a new hierarchy requirement. Cross-project
themes and shared standards may cut across that structure.

## Provocation candidates

- After selecting a project, compare an overview that opens the most relevant
  artifact with an overview dominated by current execution. Use a real pending
  foundation decision to judge what earns space first.
- Compare a dated, source-backed assessment of progress with task completion
  counts. Determine how unresolved product uncertainty remains visible even
  when agents are closing work items.
- Compare delegation from a reviewed work item with entering the execution
  session immediately. Preserve the agreed ability to visit the original
  session; examine which context and result belong in the workbench.

These candidates build on workbench-first and Flere with deep Clavain
integration. They do not authorize a Linear integration, automatic agent
selection, or a new implementation plan. The existing validated
[CUJs](../cujs/README.md) need human-reviewed reconciliation with the new
workbench direction before derivation.
