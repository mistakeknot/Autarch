Verdict: needs-changes

### Summary

Decisions 13-18 build a real security primitive — cryptographic ratification with a hard "unsigned = proposed" default — that correctly reduces the class of attack the 2026-09-22 review flagged (agent text posing as an approved action). But the design stops at the signature boundary and doesn't yet say who or what can reach the signing key, or what a frozen command's hash actually pins. Two gaps (SF1, SF2) mean the "only mk moves a fact to ruled" invariant (Ultan ruling 2), which this whole mechanism exists to make structural, is not yet structurally guaranteed: it depends on Home's process and Uqbar's write access staying separate from everything else that runs on zklw, and the document never states that separation. A third recurring theme (SF3-SF5) is that "frozen by hash" and "shown exactly" describe the command's label, not its runtime behavior or the text later fed back into an agent — both of which can drift or carry injected content that the hash and signature don't cover. I acknowledge peer fd-user-product's non-blocking finding that "everything on pick" plus no focus filter raises mis-click risk at ~98-project scale (`peer-findings.jsonl`); SF3/SF4 are the mechanism-level version of that same worry — not just "wrong click" but "correct click, wrong runtime behavior." I also acknowledge fd-architecture's blocking ARCH-1 (in-process Mycroft `DecisionQueue` still unreconciled with the bead-based decision design, carrying forward the 2026-09-22 review's P0): from this lens it matters because a second, un-reconciled queue is a second path to dispatch that this document's approval/signing model doesn't cover, so SF1/SF4's scoping questions apply there too, not just to the new bead-based continuation path.

### Issues Found

SF1. P0: No privilege separation between command execution and key custody — decision 13 says commands run "deterministically by the service," and decision 10 says Autarch is "one Go application... the engine." Decision 18 says Home signs with "its own ed25519 key on zklw, used for nothing else," but never states that the signing capability lives in a different process, account, or credential store than the one executing agent-frozen shell commands. If they share a process or OS account — which "one Go application" implies — then a single mk-approved command (decision 14: zero extra scrutiny beyond the pick) runs with enough privilege to read or use the key file directly, letting one approved command manufacture arbitrarily many future forged "ruled" files. This is the sharpest form of the assigned question "could an agent get Home to sign": not by calling an API, but by using the command-execution primitive itself, once approved, to reach the credential store.

SF2. P0: `allowed_signers` lives inside Uqbar and travels by git commit ("committed to the Uqbar, so every machine gets it through git"). The document never states who may write to Uqbar beyond "a private repo... any Aleph user can set up," nor whether adding a signer requires anything stricter than an ordinary commit (review, a second signer, a protected path). Anyone with push access to Uqbar — a compromised credential, a misconfigured automation, or (per the user's global zklw-autosync policy) a repo marked for autosync promoting a branch on a timer — can append their own public key and thereafter sign rulings that every consumer (Lattice, the feed hook) will render as fully ruled. This defeats SF1's mitigation even if execution and signing are separated, because it attacks the trust list rather than the key.

SF3. P1: Decision 14 states "the command is frozen by hash when the bead is filed, so what was shown is what runs," and decision 18 adds a pick-time re-check of "the continuation's hash and preconditions." Neither is defined precisely enough to know what's actually pinned: if the command is e.g. `bash deploy.sh` or references a project path, the hash of that string is stable even while `deploy.sh`'s contents, the target branch, or any file it reads change between filing and pick — and decisions can sit for a while (decision 18's own "stale" concept implies this). "Preconditions" is never defined, so it's unclear whether content drift in a referenced file is even a precondition the re-check inspects. Without stating that the hash covers a content-addressed snapshot of everything the command reads (or that preconditions include such checks), "what was shown is what runs" is a claim about the label mk saw, not the behavior that executes.

SF4. P1: No execution sandbox, working directory, or per-project credential scoping is stated for command continuations. Decision 10 makes Autarch a single estate-wide engine; decision 13 has that same engine run commands "deterministically." A command approved for one project's decision bead therefore has no stated boundary — cwd, env, filesystem access, or credentials — confining it to that project rather than the other ~97 the service also touches. This widens SF1's blast radius even absent a key-custody failure: a benign-looking, correctly-hashed command can still act estate-wide if nothing scopes what "the service" can reach when it runs it.

SF5. P1: Decision 17's feed hook injects, at the start of every turn, "the rulings relevant to that project... one line per item." The content of a ruling — `options_shown`, the recommendation, the question — originates from whichever agent filed the decision, not from mk; Home's signature attests that mk picked an option, not that the surrounding text is safe to hand unescaped into another agent's context. This is the same class of failure the 2026-09-22 review flagged as its lone P0 (S1: agent-authored proposal text rendered as live, actionable HTML) — here the sink is an LLM's turn context instead of a DOM, and the payload is "one line, fast, cached" rather than a button, but the document states no delimiting, escaping, or "treat as data not instruction" rule for what the hook injects. The same gap applies to "brief" continuations (decision 13): a fresh thread's "only context is the bead," so a compromised or careless asker's filed text is the sole grounding that thread has, with nothing to distinguish mk's actual pick from the filer's framing of it.

SF6. P2: "Lattice and the hooks treat unsigned files as proposed" (decision 16) reads as a presence check ("has a ratification block with a signature") rather than a stated validity check ("signature verifies against a key currently in `allowed_signers`"). A malformed signature, an expired/rotated key past its `valid-after`/expiry window, or a signature from a key not (or no longer) in `allowed_signers` should all also render as proposed — the document should say this explicitly so every future consumer (the rail, any new integration) implements the same collapse-to-proposed behavior rather than a subset of it.

SF7. P2: Decision 16 rejects a passkey/step-up tap on every pick with "Home access already equals shell access" — true for mk's own session, but the rejection implicitly assumes the only relevant principal with that access is mk. SF1 shows the design doesn't yet establish that no other process on zklw (a Mycroft-dispatched T2/T3 agent, `zklw-ci` automation, an autosync sweep) shares enough of that access to reach the signing path. The refusal is reasonable once SF1/SF2 are closed, but as written it forecloses a mitigation (step-up confirmation) before the threat it would address (non-mk processes on the same box) has been ruled out.

SF8. P3: Decision 18's stale-decision guards (rail marking plus pick-time hash/precondition re-check) close the day-scale drift window but not the execution-time one: between the re-check succeeding and the command actually running, a referenced file could still be swapped. Low likelihood relative to SF3's larger window, but worth a one-line ruling (e.g., re-check and exec happen inside one lock/transaction) so it isn't rediscovered during planning.

### Improvements

1. State explicitly, before planning, which OS account/process holds the Home signing key and whether it is disjoint from the account/process that executes command continuations — this single ruling would resolve SF1 and materially change SF4's blast-radius calculus.
2. Restrict Uqbar write access (or at minimum `allowed_signers` changes within it) to mk directly — e.g., require that file to be edited only through a path Home itself controls, not ordinary git push — and exclude Uqbar from any timer-based autosync promotion that could fast-forward a signer addition without review.
3. Define what the decision-14 hash covers (command string only vs. a snapshot including referenced file contents) and what decision-18's "preconditions" check, so "what was shown is what runs" is a verifiable claim rather than a description of the UI label.
4. Add one line to decision 17 (and to the "brief" continuation in decision 13) stating that injected ruling text and bead content are handled as untrusted data — quoted/delimited, never concatenated as instructions — mirroring the fix the 2026-09-22 review already recommended for the rail's HTML rendering.
